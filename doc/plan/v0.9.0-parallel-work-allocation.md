# v0.9.0 并行开发工作分配

## 1. 目标

v0.9.0 是 Lifly 的功能补全版本。目标不是继续横向增加新产品模块，而是把路演时会断链的真实能力补齐：账号、设备路由、E2EE、真实 PowerSync、附件/审计加密、AI Provider、Personal Compute Node、Cloud AI 授权、Android 真机闭环以及当前产品消费层遗留。

本计划专门解决多 Agent + Git worktree 并行时的文件冲突问题。

> **集成状态（2026-08-16）**：Wave 0/1/2 的并行实现已经进入 `agent/v0.9.0-final-integration` 架构收口阶段。本文件保留为历史执行分配，不再用于启动新的并行功能开发。后续只允许 Demo Delivery Hardening（native runtime packaging、签名、Desktop Companion、可复现构建、实机验收）以及发现的 P0/P1 缺陷修复；不得按旧 Agent ownership 再次复制/重写已经集成的公共 seam。

原则：

```text
共享合同先封板
目录所有权优先于功能名称
一个高冲突文件同一波只允许一个 Agent 修改
各 Agent 只跑模块级最小检查
全量 release gate 集中到集成分支
不为并行而复制业务规则
不允许各 Agent 私自改共享协议
```

正式版本集成分支：

```text
develop/v0.9.0
```

并行 worktree 可以使用临时 Agent 分支，完成后按原子提交摘取/合并回 `develop/v0.9.0`，临时分支不代表新的产品版本。

# 5. Wave 1 不建议单独开 Agent 的工作

以下内容看起来可以拆，但第一波单独开 worktree 反而容易制造冲突：

### Asset / Audit E2EE

依赖 Agent 2 的 encryption envelope 和 PowerSync contract。第一波可以只研究，不应直接抢：

```text
powersync_schema.dart
powersync_crud_mapper.dart
models.py
sync/service.py
```

### API 全业务认证接线

memos/tasks/ledger/assets/search/home/mcp 每个 router 都会被改，但它依赖 Agent 1 的 auth principal。适合在 Agent 1 合入后由一个集成 Agent 批量机械接线，而不是多个 Agent 各改一套 auth dependency。

### migration runner

需要看到最终 v0.9.0 数据模型后再落，不应该第一波就固定 migration。

### release gate / docker compose / dev scripts

应该最后统一写，否则每条分支都会抢脚本和 compose。

# 8. 简化开发流程

为了速度，各 Agent 不运行完整工程检查。

每个 Agent：

```text
1. 只读 ask-matt + 本任务相关文档/技能
2. CodeGraph / 定向搜索定位代码
3. 修改自己所有权范围
4. 只跑对应模块最小测试/静态检查
5. 原子 commit
6. 输出：改动摘要、测试结果、共享接口需求、commit SHA
```

不要求每个 Agent：

```text
完整 Flutter test
完整 API pytest
完整 pnpm test
完整 Docker smoke
完整 release gate
真机回归
跨端人工验收
```

这些统一留给 Agent 8。

但最低底线仍保留：

```text
Python 改动 -> 相关 pytest/import check
Dart 改动 -> dart format + 相关 analyze/test
TypeScript 改动 -> typecheck/相关 test
Android manifest/gradle -> build/syntax check
```

