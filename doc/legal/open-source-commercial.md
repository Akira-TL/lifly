# Lifly 源码许可与商业化策略

## 1. 当前决定

Lifly 希望源码可以被阅读、研究、fork 和修改，但不允许第三方未经授权把第一方代码拿去做商业产品。

因此当前许可方向不是 MIT、Apache 或 AGPL，而是：

```text
第一方源码：PolyForm Noncommercial 1.0.0
商业使用：单独授权
官方云服务：由 Lifly 自行运营或授权运营
第三方依赖：继续遵守各自许可证
```

因为商业用途受到限制，这种模式准确说是 **source-available / non-commercial**，不属于 OSI 定义下的 Open Source。

## 2. 允许的事情

在 PolyForm Noncommercial 许可范围内，可以：

- 查看源码；
- fork；
- 修改；
- 做个人学习、实验、研究和其他非商业使用；
- 在非商业前提下分发原版或修改版。

重新分发时必须保留许可证，以及项目提供的 Required Notice。

仓库根目录已经加入正式 `LICENSE`。当前 Required Notice 使用公开身份 `Akira-TL`；如果未来改为公司主体或其他正式著作权主体，只需要同步更新 Notice。

## 3. 未经授权不允许的事情

商业用途不在默认授权范围内。

如果第三方希望基于 Lifly 做收费 SaaS、付费客户端、商业集成、商业部署或其他以商业利益为目的的使用，需要另行取得商业授权。

具体商业边界以最终 LICENSE 和单独商业协议为准。

## 4. 为什么不选 AGPL

AGPL 的重点是 copyleft：使用者可以商业使用，只是在特定网络服务场景下需要提供相应源码。

这不符合 Lifly 当前的要求。我们的目标不是“商业使用可以，但必须开源”，而是“商业使用本身需要另行授权”。

## 5. 为什么不选 MIT / Apache

MIT 和 Apache 都允许商业使用、修改和再分发。它们适合希望最大化生态采用的项目，但不符合 Lifly 当前“不允许未经授权商业化”的要求。

## 6. 文档和设计材料

代码与非代码材料可以使用不同许可证。

产品文档、架构图、宣传材料如果未来需要单独公开，可以再决定是否使用 CC BY-NC 或保留版权。不要把 Creative Commons 许可证直接套到软件代码上。

## 7. 商业化方式

Lifly 自己仍然可以商业化，因为著作权方不受自己授出的非商业许可限制。

可考虑的官方服务包括：

- 云同步；
- 托管存储；
- 官方 AI 服务；
- 托管 MCP / Agent 接入；
- 企业或个人商业授权；
- 高级托管能力。

商业模式不以锁死用户数据为前提。

## 8. 数据可迁移原则

无论后续如何商业化，都继续坚持：

- 用户可以导出自己的核心数据；
- 用户可以删除云端数据；
- 核心能力保留本地运行路径；
- 不把无法迁移的数据锁定作为付费手段。

## 9. 第三方代码

Lifly 的许可证只覆盖我们有权许可的第一方代码。

Flutter、FastAPI、PowerSync、PostgreSQL、Redis、MinIO、Ollama、Rust/Python/Node/Dart 依赖以及模型权重，都继续受各自许可证约束。发布源码或二进制包前应生成 Third-party Notices 并检查再分发条件。
