# Lifly v0.1.0 Foundation Baseline 全量开发计划

## 1. 文档定位

本文档是 Lifly `v0.1.0 Foundation Baseline` 的全量开发计划。

它根据以下文档收口：

```text
docs/26-v0.1-architecture-freeze.md
docs/27-milestones.md
docs/28-issues-backlog.md
docs/53-local-core-bridge-foundation.md
docs/58-flutter-dart-local-core-bridge.md
docs/59-version-control-plan.md
docs/60-major-version-roadmap.md
docs/61-v0.1-full-development-plan.md
```

本计划是 `docs/61-v0.1-full-development-plan.md` 的目录化版本，后续 v0.1 收口以本文档为主。

## 2. 当前开发分支

```text
fix/v0.1-release-gate
```

分支职责：

```text
完成 v0.1.0 release gate
统一 Lifly 命名和版本
稳定 pnpm / Flutter / FastAPI / MCP / Local Core fake 基线
补齐 release 文档和验证入口
```

该分支不负责：

```text
真实本地持久化
真实 PowerSync uploadData
跨端云同步
生产级 auth
Local MCP 调用 Flutter/Dart 真实数据层
附件完整上传体验
CSV 导入导出完整 UI
```

## 3. 版本定位

```text
版本号：v0.1.0-dev -> v0.1.0
版本名称：Foundation Baseline
版本目标：第一个可验证、可继续迭代的工程基线
下一版本：v0.2.0 Local Data MVP
```

`v0.1.0` 不追求完整可用产品，而是确保：

```text
代码库结构稳定
文档体系稳定
协议边界稳定
测试入口稳定
命名和版本统一
后续 AI agent 可以按统一规则继续开发
```

判断标准：

```text
新 agent 阅读 README + docs/59 + docs/60 + 本文档后，能明确当前版本、开发边界、release gate 和下一步入口。
```

## 9. 推荐提交顺序

```text
1. fix(docs): 建立版本开发计划目录
2. fix(project): 统一lifly命名和版本号
3. fix(workspace): 稳定pnpm依赖和脚本
4. fix(mcp): 冻结v0.1工具协议
5. fix(api): 收口v0.1后端基线
6. fix(local-core): 收口本地核心fake基线
7. fix(flutter): 收口v0.1客户端基线
8. fix(release): 完成v0.1发布门禁
```

提交原则：

```text
每个提交只覆盖一个模块
提交前运行对应最小检查
最终合入 master 前运行完整 release gate
不要把 v0.2+ 功能提前混入 v0.1
不要把 unrelated 工作区改动混进规划提交
```

## 10. v0.1.0 Definition of Done

`v0.1.0` 必须同时满足：

```text
1. 命名和版本统一
2. 根 workspace 依赖稳定
3. 后端 API/MCP 基础路径可验证
4. MCP v0.1 schema 冻结
5. Local MCP/Local Core fake 链路可验证
6. Flutter 基础页面和状态边界可验证
7. 文档索引、路线图、版本控制、release gate 完整
8. 所有必须检查命令通过，或有明确环境例外说明
9. 没有把 v0.2+ 功能提前塞进 v0.1 release gate
10. `fix/v0.1-release-gate` 可以合入 master，并准备 `v0.1.0-rc.1` 或 `v0.1.0` tag
```
